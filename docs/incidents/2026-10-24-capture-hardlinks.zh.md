# 2026-10-24：Telegram 保存已提交但索引失败

## 现象与已核实原因

Ductor Telegram 的保存按钮返回“保存尚未确认: Knowledge Router exited with status 2”。
原冻结计划的变更日志实际已是 `COMMITTED`，确认绑定仍为 `pending`。

用相同运行时解释器单独执行索引刷新，稳定复现退出 2：

```text
KnowledgeRouter error: Hard-linked targets are not allowed: …/Vault/AGENTS.md
```

故障顺序为：冻结计划提交成功 → 全库索引读取硬链接来源被拒绝 → 命令退出 2 →
Ductor 未收到成功回执，保留待确认状态。旧 subprocess bridge 丢弃 stderr，导致界面只有退出码。
真实库的 2183 篇适格 Markdown 中有 1827 篇硬链接，不能通过跳过来源来掩盖故障。

恢复只读来源后，继续用真实按钮处理函数与临时确认记录验证，发现第二层故障：提交阶段
仍固定 15 秒超时，在 15.45 秒被杀死。实际索引与确认处理需要约 24.83 秒。只修硬链接
读取不足以完成按钮确认，必须给包含索引刷新的提交操作独立的期限。

## 修复边界

- 新增显式只读来源接口 `secure_read_source_bytes`；扫描与证据复验允许读取已挂载根内的
  普通硬链接文件，不跟随符号链接/重解析点，不允许路径逃逸。
- 通用 `secure_read_bytes`、控制记录、冻结计划、追加/编辑目标维持硬链接拒绝。
  `allow_hardlinks=True` 不能与 `writable=True` 组合。不解除共享 inode 的写入保护。
- 相同来源策略用于 Context 简报、状态和事件历史的来源复验，避免“索引成功但引用始终过期”。
- 仅定向修补实际运行 skill；保留其既有的 `--inspect`、`--inbox` 等宿主集成能力，未用
  发布仓库整包覆盖。旧副本保存到本机 Ductor backups，未修改原笔记、链接关系或授权策略。
- Ductor 的 `capture --commit` 使用 120 秒期限，预览/只读检查仍为 15 秒。保持原计划的
  幂等、会话绑定、目标/校验和、策略和过期验证，不允许通过更换计划绕过确认。
- bridge 并发读取 stdout/stderr，stdout 仍有上限，stderr 只保留末尾 4096 字节；失败时
  展示有界错误末行。额外输出不会堵塞子进程，也不会混入成功 JSON。

## 验证

回归首先在临时 Vault 复现：普通捕获已写入、随后硬链接 AGENTS 索引失败，命令返回 2。
修复后同一用例提交/刷新成功，重复提交为 `idempotent_replay`；硬链接笔记可检索、修改后
仍正确标记 stale；写入和控制记录硬链接继续被拒绝。运行副本的同一组测试也通过。

Router 全套 323 项通过；Ductor 两个直接相关套件 35 项通过，扩展宿主相关批次最终
253 项通过（87.80 秒）。扩展验证发现旧取消测试没有模拟 stderr 管道，出现 Windows
测试清理异常；补齐模拟进程契约后，单项取消回收及整个扩展批次均通过。

真实原计划续接返回退出 0、`success`、`idempotent_replay`，目标文件 SHA-256 前后相同；
索引覆盖 2183 篇，`skipped_io=[]`、`skipped_decode=[]`。随后使用同一真实冻结计划和临时
会话确认副本调用完整 `confirm_capture`：返回“已保存”，临时状态变为 `saved`，耗时 24.83 秒；
目标文件和真实确认记录的字节均未改变。没有模拟 Telegram 消息或代写真实会话授权。

Router 修补通过新建子进程即时生效。主进程的期限和 stderr 修复则需要正常重启：先核实
没有活动子进程/在途任务，并用修改前备份计算指纹，确认启动以来只有本次两个源码文件变化，
再通过原有 PM2 `ductor` 服务正常重启。重启后进程存活、Telegram 恢复轮询，运行身份与磁盘
源码指纹一致。真实确认记录保持 pending，由用户再次点击原按钮完成 bot 自己的确认步骤。
