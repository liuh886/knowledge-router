# 开发计划（Context Base）

这份文档是 KnowledgeRouter 的**开发计划与接手说明**。它记录：现在到了哪一步、哪些决定已经定下、
剩余交付项各自要达到什么、以及下一轮如何继续。它面向两类读者——继续开发的 agent，以及决定优先级的人。

与其他文档的分工：

| 文档 | 作用 |
|---|---|
| 本文 | 计划、决策、验收条件、接手顺序 |
| `TASKS.md` | 逐项勾选的实现清单与历史记录 |
| `EVALUATE.md` | 已实际验证过的质量结论（按日期追加） |
| `docs/*review*.zh.md` | 独立复核记录，含当时复现的缺陷 |
| `docs/context-base-landscape-and-roadmap-2026-09-22.zh.md` | 同类产品调研与方向论证 |

本文不重复论证方向，只承载"接下来做什么、做到什么算完成"。**计划变更应先改本文**，再落到 `TASKS.md`。

## 2. 已完成

按主题列出，括号内为对应提交。

**解析与诊断的正确性**
- 单一链接解析器，供诊断与关系图共用，两者不可能给出不同结论。
- 解析规则对齐 Obsidian 官方文档（带路径按路径、裸名称按唯一文件名、再唯一别名），并做有界词法归一化
  （`../`、`./`）。`uncertain` 的情况只报告、不擅自判定。（`7d063f1`、`fe323e6`）
- 断链按出现位置给出 `triage_hint` 与原因，原始总数始终保留；`confidence` 恒为提示。

**复查议程的可信性**
- 复查 `basis` 为**语义基线**：Context 修订、定义指纹、诊断版本。任一变则拒绝比较，消失项不计作已解决。
- 不完整基线：返回 `incomplete`（顶层字段 + 警告行），**退出码 2**，且不会因为"有事项"而被掩盖。
- 显示截断（`--limit`、`--code`）只影响显示；台账、指纹、增量始终用全量。（`bd1187a`、`fe323e6`、`b8c3dec`）

**重复断链与孤立笔记**
- `contexts converge`：把重复断链收敛为"一个目标一次决策"（大小写不敏感），给出建议与证据；
  机器噪声默认排除但如实计数。（`72101c2`）
- 孤立笔记进入复查议程（`orphan_note`），范围与计数在**全量 occurrence 流**上判定，不从显示样本推断。

**派生卡片的可追踪性**
- 每张卡片登记真实输出路径、单 Context 指纹、`{来源: 校验和}` 与**编写依据**
  （`--expected-source-snapshot` 校验；未提供则标 `unverified basis`）。
- 登记读取区分 `absent / valid / unreadable / invalid`；登记损坏时 basis 不完整、不算已解决、退出 2。
- 卡片被外部修改会被标出。（`b8c3dec`）

**知识页（P1）**
- `contexts page publish`：外部知识区、带版本、含依据 manifest。
- 强制区分**引用**与**推断**：引用必须指向真实笔记（记校验和），推断必须标注且无引用，
  `[conflict]` 至少两来源；引用不存在的笔记或越界行号**直接拒绝**；无标记条目拒绝。
- `contexts get`（按预算、放不下的主张省略并计数）、`contexts expand`（展开到当前来源，
  返回 `current/changed/missing`）。（`6ce95a1`）

**状态瘦身与性能**
- 历史 `bindings` 只保留最新版（855 KB → 232 KB）；索引去掉从未被查询的 trigram 表（102 MB → 51.8 MB）；
  schema 版本并入 generation 哈希，换版会重建而非复用。（`72101c2`）
- 一次 `review` 只读一次快照（原为两次）；无启用策略时不计算来源基线。
  实测：poll 14.09s → 0.03s，review 33.3s → 22.0s。（`f479337`）

**计划与文档**
- 路线图落为带验收条件的交付项（`TASKS.md`）；发布 3 份路径干净的复核/调研文档。（`ce3e956`、`02f68c7`）

## 3. 已确定的设计决策

这些是已经定下的，不是待选方案。改动需先改本节并说明原因。

1. **知识页是 Vault 外的派生物**（方案 (c)）。需要写进 Vault 时仍走既有 capture broker 的两步预览/提交，
   `append-create` 策略下授权。**不新增写入原语。**
2. **别名编辑目前无法表达。** broker 只有"追加既有文件"与"新建文件"，改 frontmatter 需要新的写入原语。
   在真正需要之前不造它；需要时按一个新原语对待（全文 CAS、崩溃对账、变更回执、语义版本）。
3. **工具不代写正文。** 生成物（卡片、知识页）的正文由调用方（agent 或人）撰写，工具只校验依据、控制范围、
   保存版本、解释变化。
4. **引用与推断必须可区分，且引用必须可核实。** 无法核实的引用与编造的引用无法区分，因此直接拒绝。
5. **不确定就不判定。** 歧义保持歧义、未定义回退只报告、孤立只提示。任何"计数依赖未定规则"的数字都是
   报告而非结论。
6. **不把派生摘要混入原始来源索引。** 否则总结会被当成独立证据再次引用。
7. **不引入向量库、常驻服务、独立记忆系统**，除非有实测瓶颈作为依据。
8. **发布绑定依据。** 每次发布记录其来源快照、Context 定义指纹与整理规则版本（诊断版本）。

## 5. 明确的非目标

- 不追求"把孤立笔记清零"。孤立信号用于**发现**内容，不是必须完成的待办。
- 不批量创建占位页来改善数字。占位页只提升链接可解析性，**不证明知识增长**；
  已创建的占位页标记 `stub: true`，应与成熟概念页区别对待。
- 不以命令数量、索引数量、诊断计数衡量进度。
- 不引入向量数据库、常驻服务、独立记忆系统作为前置条件。
- 不做未经实测收益的复杂度。

三类结果分别报告，不合并成一个"更好"的分数：

1. **结构已连接** —— 链接有落点（可解析性）。
2. **知识有内容** —— 页面有实际结论且来自独立来源。
3. **使用有帮助** —— 后续任务确实使用并减少错误或重复阅读。

## 6. 已知未验证或未证明的边界

诚实清单。以下都不是"已修好"，只是"目前这样处理"。

| 事项 | 边界 |
|---|---|
| `../`、`./` 路径解析 | 参考 Vault 中此类链接为 **0 条**，该修复只由合成测试证明，未改变真实库任何计数 |
| `[conflict]` 主张 | 真实库尚未发布（未找到经核实的来源冲突），该路径只由测试覆盖 |
| token 预算 | 是**估算**（CJK 字符计 1、其余计 1/4），不是分词器 |
| 卡片登记 | 只能覆盖它存在之后发布的卡；旧卡依赖默认路径 + mtime 回退 |
| `unverified basis` 卡 | 只被标出，不自动补正 |
| 性能数字 | 一台机器、一个 Vault、一次运行，非通用结论；`diagnose_vault` 未优化 |
| 歧义与未定义回退 | 仍然不判定；相关计数是报告而非结论 |
| 分类提示 | 是分流便利，不是完整性证明 |
| 竞品对比 | 调研文档中的星数与能力对比**未经本机复测**，应读作阅读清单 |
| 真实库语义正确性 | 未解析 6,251 处中约 89% 出自单个自动生成目录；这是分流结果，不等于修好了这些链接 |

## 8. 如何验证现状

全部命令均为只读（`--no-record` 可避免写台账）。把 `<NAME>` 换成本机登记的 Vault 名。

```bash
python scripts/knowledge_router.py doctor   --vault <NAME> --details --json
python scripts/knowledge_router.py contexts review   --vault <NAME> --no-record --json
python scripts/knowledge_router.py contexts converge --vault <NAME> --json
python scripts/knowledge_router.py contexts page list --vault <NAME>
python scripts/knowledge_router.py contexts get research:ccs --vault <NAME>
```

在参考 Vault 上应看到（与第 1 节一致）：

- `review`：事项 2,734；`counts_by_code` 为 `compiled_card_stale 1 / broken_reference 2255 / orphan_note 475 / ambiguous_reference 3`；
  `basis.complete=true`、`incomplete=false`；`card_registry_state=absent`；
  `maintenance_status=no_policies`、`maintenance_configured_contexts=0`。
- `converge`：`configured=true`、目标 146；建议分布 `create_or_relink 117 / needs_judgement 25 / check_naming_variant 4`。
- `page list`：两张页面均 `stale=False`。

测试：`python -m pytest`（273 项）与 `python -m ruff check scripts tests`。

**不要把"当前没有发现"读成"没有问题"**：`incomplete=true` 时结果不代表全部；`configured=false` 时不代表
范围为空；登记不可读时不代表没有卡片。

## 9. 下一个窗口的接手顺序

1. 读本文第 1、3 节，再读 `TASKS.md` 的路线图段落，确认基线未变（提交号不同则先看新提交）。
2. 跑第 8 节的验证命令，确认数字与本文一致；不一致先查原因，不要直接开始新功能。
3. 若继续 C：先确定试点 Context 与资料，再按 C 的验收条件做；**影响的定位方式**先按整页粒度。
4. 任何"改好了"的结论都必须有：一次复现 → 一次修复 → 一条回归测试 → 一次真实库或合成用例的验证。
   合成用例要明确标注为合成，不得充当真实库改善的证据。
5. 完成后追加 `EVALUATE.md` 条目，并更新本文第 1 节快照与第 4 节状态。
