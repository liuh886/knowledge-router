## 三组优先修复的问题

### 1. 卡片绑定的是保存时的来源，未必是编写时使用的来源（高优先级）

位置：[context_compile.py:433](../scripts/context_compile.py:433)，尤其第 467–468 行。

当前 `write_compiled_card` 先落盘正文，再重新扫描范围内来源，把那一刻的 checksum 登记为依赖。它没有接收前一步 compile bundle 的固定身份或来源清单。

临时库复现：

1. 来源写着 `decision: OLD`，生成编译包和旧内容草稿。
2. 来源改成 `decision: NEW`。
3. 保存仍写着 OLD 的草稿。
4. 卡片登记的是 NEW 的来源哈希；review 返回 `clear`，没有卡片过期提示。

这不是要求系统证明所有自然语言结论。只需先满足更基本的保证：**记录的版本确实是生成/审核草稿时使用的版本。**

建议让 compile 返回不可变 bundle ID 或 manifest；save 必须提交该依据，落盘前校验来源和定义未变化。自由导入的正文若没有可验证的编写依据，应标为 `unverified_basis`，不能自动获得“来源未变”的可信含义。来源版本失配则拒绝发布或要求重编译。

把正文与登记记录视为一次可恢复发布。`card_sha256` 已保存，也应在读取时用于识别外部改动，并返回“人工/外部修改待复核”，而非把被修改正文默认为原发布内容。

此外，[context_brief.py:52](../scripts/context_brief.py:52) 会纳入 Context 关联事件的来源；当前 `scoped_source_dependencies` 只取目录/标签范围。后续 manifest 应记录实际使用证据（含范围外事件或项目证据），另存用于发现新资料的观察范围，避免将两者混为一份清单。

### 2. 卡片登记损坏会让过期事项被判定为已解决（高优先级）

位置：[context_compile.py:389](../scripts/context_compile.py:389)、[context_review.py:163](../scripts/context_review.py:163)。

`load_compiled_cards` 把 JSON 解析失败等情况转成空列表，调用者无法区分“没有登记卡片”和“登记数据读坏了”。review 的完整性依据也未包含卡片登记读取状态。

临时库复现：一个自定义路径卡片因来源修改被报告过期；随后将临时登记文件改成损坏 JSON，再执行 review，结果是：

```text
status: clear
basis.complete: true
delta.comparable: true
resolved_item_ids: [原来的过期卡片事项]
```

卡片没有修复，只是登记无法读取。

建议返回明确的 `absent / valid / unreadable / invalid` 读取状态，校验必要字段，把异常纳入 review basis；读取失败时禁止产生 resolved。写入端也应拒绝在损坏登记上以空列表重建，避免覆盖其他记录。

### 3. 先汇总和截样，再判 Context 范围，会漏报和错计（高优先级）

位置：[vault_doctor.py:143](../scripts/vault_doctor.py:143)、[context_review.py:75](../scripts/context_review.py:75)、[link_convergence.py:147](../scripts/link_convergence.py:147)。

doctor 对每个目标只保留排序后的前 20 个来源，review/converge 又拿这份展示样本判断目标是否属于 Context。

临时库复现：前 20 份来源都在范围外，第 21 份位于所选 Context，21 份都含 `[[Missing]]`。全库 doctor 正确统计 21 次，但 converge 返回 0 个目标；review 返回 `clear` 且 `basis.complete=true`。

另一用例：范围外 3 次、范围内 1 次，指定 Context 后 converge 仍统计 4 次。

建议对完整 occurrence 流先做范围筛选，再按目标聚合、统计 hint，最后裁剪展示样本。维护原始全库总数时，应另列字段，不要把它当成当前 Context 的次数。默认噪声过滤也应基于范围内 occurrence，避免范围外的主导 hint 影响本范围决策。

## 可以同批收尾的三个边界

| 问题 | 本次实证 | 建议 |
|---|---|---|
| 卡片指纹覆盖全体 Context | 给库新增一个无关 Context，旧 Context 的卡片也报 `compiled_card_scope_changed` | 单卡采用所属 Context 的语义指纹；全库 review 另保留集合指纹。卡片用途、名称等若影响编译输入，也须纳入对应依据 |
| 无定义的 converge 返回“完整空结果” | 没注册 Context 的临时库，CLI 返回 exit 0、targets 0、scan_incomplete false | 显式标记 unconfigured/incomplete；不存在的 `--context` 应报错。保持与 review/coverage 一致 |
| 新建成功不等于链接已解决 | `[[Missing]]` 配 `--target-path Area/Different.md` 可 stage/commit 成功，但仍有 1 条断链 | 在预览中使用统一 resolver 验证拟建路径将解决哪些 occurrence，列出剩余/歧义；不要仅验证文件名没有被 broker 改写 |

这些是对现有契约的收紧，不需要为每项新增一个命令或子系统。

## 产品上应避免的下一步偏移

### 补上发布到使用的缺口

当前 `load_compiled_cards` 的消费者是登记写入和 review；search/brief 的查询路径没有读取已发布卡片的逻辑。这意味着“卡片已保存并能检查过期”还没有自动转化为“下一次 agent 可以使用整理后的知识”。

这是下一阶段最值得补的产品能力：一个明确的 Context 读取入口，优先呈现已发布且依据有效的知识页，并能展开原始证据；卡片过期或依据不完整时说明状态并回到原文。不要直接把生成卡片混入原始来源索引，否则可能将总结再次当成独立证据。

### 不用空页面换取更好看的质量数字

converge 的默认内容是“待补充”占位。作为人工起草入口可以保留，但批量新建占位页只能改善链接可解析性，不能证明知识增长。

建议分别报告：

- 结构已连接：链接有落点。
- 知识有内容：页面有实际结论及独立来源。
- 使用有帮助：后续任务确实使用且减少错误或重复阅读。

占位页应显式带 stub 状态，在知识上下文中降权或标示，不要与成熟概念页等同。高频的 CCS 缺口可以引导一个有依据的概念页试点，而非一次性生成大量空页。

### 孤立不等于无价值

日报、收件箱、原始文献可能本来就不需要反向链接。孤立信号适合帮助发现内容，不宜默认成为必须清零的待办。可按 Context 用途、页面类型、近期任务相关性排序，并保留“暂不处理”的理由。

### 将方向写进执行清单

研究报告已经发布，但 TASKS 的 Open 部分仍主要列激活、远程投递、旧文提取、图排序和可选语义检索。尚未把上下文包、绑定版本发布和单 Context 更新闭环转换成明确交付项。

建议把路线从研究文档落实到 TASKS：每项写清用户触发、交付结果、验收条件。研究结论被链接到文档索引不等于已经进入开发队列。

## 建议的下一批工作

### A. 先收紧现有正确性契约

完成三组高优先级问题，并补充各自最小回归用例：旧草稿配新来源、登记损坏后误报解决、第 21 个来源的范围漏报。单 Context 指纹、无定义 converge、新建路径可解析性一并收尾。

这一步只做现有模块重构。先不用上图数据库、独立记忆服务或全库自动学习。

### B. 紧接一个有内容的知识页试点

选择已有 `research:ccs`，用少量真实来源建立一张有当前认识、依据和未决问题的知识页。用更新后的发布契约保存并登记，让新会话能取得它，同时展开到原文。

再加入一份支持或冲突资料，完成“发现影响→修改草稿→校验依据→发布新版→下一会话使用”的全流程。涉及真实资料或维护策略的实施，应按用户随后授权的具体范围执行；本次评审未启用任何自动流程。

验收不要求自动写出所有领域结论，允许现有 agent 负责综合。Knowledge Router 首先负责找到依据、控制范围、保存版本和解释变化。

### C. 再统一读取与增量维护

以试点实际触发的调用为依据，统一 search/brief/compile/review 的来源读取和快照。把昂贵扫描与知识整理从新会话路径移走。分别计量查询延迟、新来源可见时延、页面更新成本与成功任务 token，避免只用 FTS 内部耗时代表整体体验。

下一轮最有说服力的进步不是测试从 236 增至更多，而是：**同一研究问题的已发布认识能随证据更新，更新理由可追溯，另一个 agent 可以直接接着工作。**
