# Knowledge Router 开发进度评估与下一阶段计划

评估日期：2026-09-22（Asia/Shanghai）。本报告基于本机源码、实际配置、历史验收记录和本轮复测；不是仅按 TASKS.md 的勾选数计算完成度。

## 结论

**当前已是具备较完整安全边界和回归测试的本地知识工具，正在从检索/记录工具走向 Context 管理；持续维护和实际对话接入尚未形成可靠闭环。**

下一阶段建议定位为“可追溯的 Context 工作台”：围绕少量真实主题，完成查证、状态卡、复查、确认记录、下次继续使用。优先补齐正确性和实际运行，再根据失败样例决定是否增强语义检索。

不建议用一个整体完成百分比表达当前状态。安全捕获、检索、Context、自动运行、产品分发的成熟度相差很大，测试通过也没有覆盖本次发现的新问题。

## 3. 本轮验证和真实运行差距

### 验证结果

- 本机 Router 全套隔离测试：**188 passed，113.56 秒**。一个警告来自备份篡改测试中故意重复的 ZIP 条目。
- Ductor 接入和配置热更新测试：**42 passed，4.81 秒**。
- 独立 Router 仓库静态检查：`ruff` 的 E4/E7/E9/F 检查通过。
- 实际 Vault 的现有检索集：**22 条**，其中词面 10、改述 7、应拒答 5；17 条正例全部命中预期路径且位于首位，5 条拒答均为空结果。
- 按现有评测器定义，Recall@K、MRR、拒答指标和引用字段覆盖均为 **1.0**；3 次热查询重复共 66 个延迟样本，P50 **7.56 ms**、P95 **43.61 ms**。

这些指标的适用范围有限：Recall@K 实际计算的是正例是否命中至少一个预期文档；引用覆盖检查字段齐全，不证明回答内容正确。延迟是进程内热查询，不包含 CLI 启动，也不代表完整 Context 扫描、卡片编译或带模型的问答耗时。当前拒答样例多为明确虚构查询，尚不足以验证“主题相关但证据不足”的困难拒答。

历史验收记录中的完整 Context/编译/复查耗时可达约 12 / 21 / 42 秒，不能与上述毫秒级热查询混用。该历史耗时本轮没有重测，不作为新的性能承诺。

### 当前配置与回执

本轮 `status --vault zhihaol --json` 和 Ductor 配置读取显示：

- Context 定义修订版 **5**，登记 **6** 个 Context，维护启用 **0** 个；全部是缺失 maintenance policy，而非已经定期维护完成。
- 六个 Context 的显式状态均为 `evidence_gap`。这是“缺少可投影的显式声明”，不等于原始笔记没有资料。
- Vault 策略是 **`append-create` + `capture_mode=explicit`**，并非 README 所写的关闭状态。能力已开放，但每次实际记录仍需要符合明确授权范围。
- Ductor 配置为 **`knowledge_router.enabled=false`**，Vault 选择为空、entrypoint 为空。
- Router 报告通知 **`configured=false`**；未发现完整维护周期的 `last_successful_cycle` 或成功 baseline。

- 历史文件记录了定时触发验收；本轮没有进一步证明当前定时器仍活跃，也没有触发通知或重新配置调度。

因此，“有检索能力”“执行过维护”“有定时巡检记录”“已维护每个 Context”“用户收到提醒”必须分别计量。

## 4. 已复现的优先问题

以下验证仅使用系统临时目录和合成笔记，未修改真实 Vault，也未改实现。

### P0：减少显示数量会产生假的“已消解”

来源：`scripts/context_review.py:112` 在质量项生成时提前截断，`:263` 将前后 item id 集合差直接认定为已消解。

复现：同一篇笔记含两个未解决链接；先运行 `review(limit=20)`，再运行 `review(limit=1)`，笔记字节完全不变。第二次却报告 **1 个 resolved item**。

影响：优先级变化、列表截断或 limit 变化可能被误报成维护成果。历史“已消解”计数在重算前不能直接用作质量改善证据。

修复方向：把完整观察集合与展示集合分开；没有完整覆盖时使用“未观察到/移出当前展示”，不能判为消解。覆盖范围、定义修订、诊断版本变化也应触发重新建立比较基线，而非直接比较旧 id。

### P0：不完整扫描仍可能显示 clear

来源：`scripts/context_review.py:287` 顶层状态只看是否有 items；底层 `scan_incomplete` 单独回传。`knowledge_router.py` 的 review 分支固定成功退出。

复现：模拟底层 poll 为 `status=incomplete`、`scan_incomplete=true` 且空列表，顶层返回 **`status=clear`**。

影响：使用顶层状态或退出码的调用端可能把未知状态解释为无事可做。

修复方向：扫描完整性优先于 clear；合并 poll 和本轮来源扫描的完整性信息；失败/不完整结果不得确认消解或推进成功基线；CLI 退出码与状态一致。

### P1：外部状态卡没有纳入过期检测

来源：`scripts/context_review.py:127` 只检查 Vault 内建议路径；`scripts/context_compile.py:331` 的默认保存路径已改为 Vault 旁边的外部编译区，并允许自定义目录/文件名。

复现：实际调用 `write_compiled_card` 生成外部卡片，使卡片早于来源文件，然后运行 review，**没有任何 compiled_card_stale 项**。

影响：最新交付的默认保存方式与既有更新检测脱节；用户会继续看到过期摘要。

修复方向：记录卡片身份、实际路径、Context 修订和完整来源哈希依赖清单；按内容依赖失效，而非只猜文件名或比较 mtime。支持默认/自定义输出和删除/移动来源场景。

### 工程与产品债务

- 文档中的“写入关闭”“分发仓库仍是未来工作”已与配置或源码不一致，当前事实与历史记录混排。
- Ductor 接入在运行工作区中尚未提交，缺少可复现的接入版本边界。
- 两份 Router 源码目前相同，但持续手工同步会增加漂移风险。
- `pyproject.toml` 设置 `py-modules=[]` 且没有 console entry point：当前适合源码/skill 调用，不能把 pyproject 文件存在当作安装命令已经交付。
- 图中大量未解析链接需要区分概念占位、附件、别名、路径变化和真正损坏。断链数量本身不能证明笔记质量低，也不应驱动批量生成没有依据的概念笔记。

## 5. 开发方向的论证

| 方向 | 收益与证据 | 成本/局限 | 决策 |
|---|---|---|---|
| 修正 review/compile 的维护语义，跑通实际 Context 闭环 | 直接解决本次复现问题；已有事件、回执和卡片机制可以复用 | 需要补齐跨模块状态与真实验收 | **优先** |
| 立即增加向量数据库或 embedding | 可能改善词面难以覆盖的查询 | 现有样例没有暴露召回缺口；增加索引、一致性和运行依赖也无法解决错误消解/关闭的集成 | **先扩评测，再按证据决定** |
| 立即强化全图排序 | 能利用已有关系导航 | 大量目标未解析，图生成时间和来源变化需要治理，尚无图排序增益测量 | **先做关系分类和新鲜度，再做对比实验** |
| 批量重写笔记或自动补齐概念页 | 表面上可迅速降低断链数 | 易产生无依据内容，冲淡原始资料，不解决事件和卡片来源一致性 | **不作为主线** |
| 先做完整 UI / 多平台发行 | 降低使用门槛 | 当前正确性和维护闭环仍有缺口，UI 会把这些问题包装成可靠能力 | **后置；先提供少量稳定任务入口** |

推荐主线：**原文 → 可验证证据 → 审核后的状态卡 → 完整性可信的复查 → 授权事件记录 → 再次读取。**

状态卡是派生视图，原文仍是事实来源。回答不能仅凭卡片标题或更新时间认定内容新鲜；卡片过期、冲突或证据不足时，应回到具体来源并说明缺口。

以下为一名熟悉现有代码的开发者的工作量估计，不是承诺日期；实际部署窗口、用户语义确认和连续运行观察另计。

| B：真实单 Context 闭环 | 3–5 人日 | 选一个 CCS/当前业务主题；设定明确职责与复查策略；跑完查证—状态卡—变化—复查—确认记录—再次读取；完成主 Ductor 新会话接入与关闭开关验收 | 真实对话能引用来源；原文变化导致卡片失效；中断重试不重复记录；关闭开关后新请求不再注入；没有未经授权的写入 |
| C：持续运行与最小交付 | 3–5 人日 | 选定一个调度归属，统一 `maintain --with-tick` 回执；做一个 MessageBus 通知适配器；记录实际输送结果；明确任务结束时是预览还是授权提交 | 重启后恢复；同一事项重跑不重复入队；发送失败可追踪重试；完成/取消后不继续提醒；保持安静的无变化周期与可行动通知都在连续观察中验证 |
| D：效果评测与使用收敛 | 2–4 人日 | 50–100 条真实问题集；卡片/原文证据混合读取规则；耗时分解；少量稳定自然语言任务入口；安装更新说明 | 按问题类型分别报告召回、过时证据识别、状态冲突、引用有效性、困难拒答和端到端 P95；只在测得收益后扩大排序或语义检索 |

总计约 **10–17 人日**，另加至少 **7 天观察窗口**。单人推进可按 3–4 周安排，若真实语义定义或运行窗口延迟，应调整日历，不降低验收门槛。

具体实施顺序：

1. 首个改动集中修复 review 的“消解/完整性”契约，不同时扩检索算法。
2. 为编译卡建立外部 manifest，覆盖自定义路径、来源删除、定义变更与重复更新。
3. 定义一个范围小、价值明确的试用 Context。当前 `project:main`、`contact:main` 是宽泛集合，不宜直接当作所有项目/人物的状态维护对象。
4. 验证 Ductor 当前加载代码、启动归属和回退方式，完成一个主 agent 的新会话查询。当前钩子跳过续接会话；后续扩展应显式定义换题、后台任务、完成事件的触发规则。
5. 统一调度后再接远程通知，区分“已入队”“输送端已确认”和“用户已读”。无法证明已送达时保持未知，不承诺端到端 exactly-once。
6. 收集真实失败样例，先优化慢扫描、无关资料和状态冲突，再判断 embedding/更多图排序是否值得投入。

## 7. 下一阶段应看什么指标

- **正确性**：假消解数、不完整扫描被判为清晰的次数、丢失的卡片失效事件，目标均为 0。
- **证据可靠性**：引用可回溯率、内容变化识别率、当前状态与历史记录区分正确率。
- **使用价值**：一周内真正帮助决策/推进工作的状态卡和复查事项数量，而非总生成字数或建卡数。
- **运行闭环**：明确启用维护的 Context 比例、最近完整成功周期、失败恢复结果、可行动事项送达回执。
- **性能**：分别计量 search、Context brief、compile、review 的进程级 P50/P95；先测基线，再设本机预算，避免用热查询毫秒数代替整体体验。

进入下一阶段的判断应是“一个真实主题能稳定闭环”，而不是“又增加了若干 CLI 命令”。
