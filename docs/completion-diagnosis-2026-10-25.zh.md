**工程质量与维护性**

最近完整回归记录为 440 项通过（98.31 秒）。本轮 ruff 对 scripts/tests/integrations 通过；fts_indexer.py、vault_service.py、knowledge_router.py 与最近启用验收哈希一致。本轮未重复跑完整套件，440 是近期验收证据，不是新的一轮测试结果。

优点是数据归属明确、写入边界有实际代码和故障测试、未知/过期有显式表达、恢复凭据在外部且不依赖某个模型。诊断能发现缺口而非自动把它们当作已解决。

主要风险：运行入口直接指向开发工作树，代码改动会影响下一次命令；当前存在大量未提交修改，生产运行版没有单独冻结标识。现有备份能恢复，但不等于经过验证的一键运行版本回退。CLI 1,437 行、索引模块 1,305 行，继续增功能会提高跨模块回归成本；后续宜在契约测试保护下逐步整理边界。文档同时保留多批历史状态和追加说明，当前状态需要一个可快速核对的入口。

当前“semantic routing”主要是确定性名称/别名/关键词规则；检索主要是 FTS/CJK。是否需要向量或重排，应由新问题的召回评估决定，不能以功能名称或小型测试集推断真实语义理解能力。

**下一轮的优先顺序**

1. 冻结可识别运行版本：保留单一源码主源，通过已测试的 tag/发布快照部署，稳定入口指向明确版本，记录版本/源码指纹并演练回退。整理当前验收表，区分已实现、已启用、已验证使用效果。
2. 做一次 Agent 真实任务验收：用确有来源的问题启动新会话，观察非空检索、模型前注入、实际引用和任务结果；同时验续接不重复、过期/不可用披露。配置 enabled=true 不替代这条证据。
3. 完成一个真实知识更新闭环：以一个研究 Context 为试点，处理支持、冲突、替代与无关来源，输出主张级影响与草稿，保留冲突，复核后发布下一版，并在下一会话使用。不是自动大规模重写。
4. 收敛日常维护：明确哪些 Context 要维护，按需更新项目目录索引；把结构噪声、数据待核验和当前行动分开。优先回答“这周应该更新哪一页、补哪一份证据”，而非增加用户清理数千项的负担。
5. 在真实使用结果基础上推进 Ownly 只读适配及更广的召回评测。全源扫描进一步提速属于后续独立一致性设计，不应挤占上述产品验收。
