# 增量索引与恢复（2026-10-25）

本轮目标是减少日常小改动后的建库工作，同时完整检测外部变化。采用已验证不可变索引的字节复用；没有引入文件监听服务、额外数据库或只依赖修改时间的内容缓存。

## 实现与一致性

1. 实时枚举并读取全部 Markdown，计算内容哈希。最多四个目录读取任务并行，各自持有独立安全文件句柄，结果按路径稳定排序。
2. 有可验证的活动索引时，创建独立候选副本；只更新新增、变化、删除的笔记及其 FTS/CJK 检索数据。移动按旧路径删除、新路径新增处理。
3. `index.<generation>.verified.json` 绑定索引格式、Vault 身份、来源版本和整个数据库文件的 SHA-256。复制时校验实际复制的字节，而非看 mtime/size 或文件名推断可信。
4. 旧索引没有凭据时，完整检查记录、正文哈希、FTS 与 CJK 数据；凭据不匹配或旧库损坏时回退全量构建。凭据是可重建缓存，不是新的个人事实源。不要手工生成凭据来认可未知索引。
5. 第二次完整源扫描通过后才发布候选文件。构建、活动指针更新及旧索引清理持有同一把每 Vault 锁，避免较早任务覆盖较新结果。
6. 索引/凭据发布失败时保留旧指针，重试可以复用完整但未发布的候选。已经写入原始记录而索引失败，仍用既有 applied_pending_index + 冻结计划恢复，不重新记录。

没有可继承内容时直接全量构建。`kr sync --full --vault zhihaol --json` 可主动完整重建和压缩；正常捕获自动刷新，不要求用户定期手工执行。数据格式版本未更换，旧库可在实际验证后使用。

FTS 与兜底检索增加明确的路径顺序，避免增量重插改变内部行号后使同分候选与全量建库不同。

## 证据与测量

全部写入测试均在临时 Vault 或派生文件中进行；正式年表、交易与持仓未添加测试数据。使用真实 2,370 篇 Markdown 的字节相同临时副本做端到端测试。

| 对照 | 原实现/全量 | 新实现/增量 |
| --- | ---: | ---: |
| 同语料、单篇变化的建库阶段 | 5.664 秒 | 2.096 秒 |
| 整次刷新，先旧后新 | 14.547 秒 | 13.012 秒 |
| 整次刷新，先新后旧 | 27.179 秒 | 17.421 秒 |

构建阶段约减少 63%。两轮整次刷新都更快，但系统波动明显，样本不足以形成延迟 SLA，也不能承诺整体秒级。四个逻辑数据表完全一致；两轮索引来源版本相同，五个代表查询全部一致。每次变化只改写 1 篇，继承其余 2,369 篇；前一代文件哈希不变。

有界目录读取的两次采样：单任务 6.416/5.245 秒，四任务 4.793/4.723 秒。这是本机小样本，不能推广为所有磁盘的固定收益。

第一轮未经字节凭据优化的增量实现为 5.812 秒，全量为 5.775 秒，未被作为提速成果；重复计算旧库全部派生数据抵消了收益。最终实现使用上述完整文件哈希绑定，保留无凭据场景的严格检查。旧库第一次验证可能仍较慢。

完整回归：440 项通过（98.31 秒）。覆盖同大小/同修改时间的修改、外部新增/移动/删除、多个损坏类型、凭据损坏与复制中途变化、并发刷新、发布失败及恢复、全量构建入口、并发/串行源覆盖一致性、同分检索一致性。

原始报告与可重跑脚本：本机 `~/.codex/backups/incremental-index-20261025-111011/`，包含 index-comparison-verified-bytes.json 与 pipeline-comparison.json。正式库启用结果见 EVALUATE.md。

## 仍保留的成本

每次刷新仍须两次完整源文件校验。下一阶段如要避免这些读取，需要能够证明跨进程、外部编辑和丢失事件时的一致性，例如可靠变更日志及可检测缺口后的全量回退；不能直接以 mtime/size 相同替代内容验证。本轮没有引入这种服务或降低校验要求。
