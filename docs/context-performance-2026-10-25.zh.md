# Context 查询性能优化（2026-10-25）

本轮先解决高频明确范围查询，保留全局搜索、完整发现与索引激活的校验规则。产品上优先让用户已经指明的 Context 快速可用；架构上复用原来的源文件读取与证据复核，不增加跨进程内容缓存或后台服务。

## 原因与改动

真实库共 2,370 篇 Markdown。原实现读取一个已登记 Context 时，也会全库读取和全量发现。性能剖析中，2,370 篇笔记触发了 342,044 次标签解析。

- 明确注册 ID：读取其 scope 内内容及关联事件源，不重新推断全库 Context。
- 名称和推断 ID：保留全局发现，避免静默选择同名对象。
- 一次完整发现：每篇笔记的标签只解析一次。
- 源路径仍实时枚举，选中内容仍实时读取，返回证据前仍复核哈希；不靠修改时间猜测内容未变。
- 新增 source_generation_scope 字段，明确范围摘要与全 Vault 摘要的区别。

## 测量与正确性

基准采用本轮修改前的三个模块备份，以模块路径断言确认确实运行原实现。所有调用顺序执行，没有并发跑回归测试干扰。

Biography 相同查询各重复 3 次，包含 Python 进程启动：

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 中位耗时 | 10,511 ms | 980 ms |
| 本次样本最大值 / p95 | 11,834 ms | 995 ms |

仅 3 个样本的 p95 接近最大值，不是稳定的生产 SLA。五个 Context 各一轮新旧对照，证据片段、来源数量和记录状态完全一致；新实现约 840–924 ms，原实现约 10.6–11.3 秒。原始报告在本机 `~/.codex/backups/router-performance-20261025-105442/performance-comparison.json`。

新增测试覆盖不读取范围外正文、重叠 scope 去重、新增/移动/删除即时生效、范围内编码错误、关联事件、并发修改复核、非法范围、名称歧义与每篇标签只解析一次。完整回归最终结果见 EVALUATE.md。

## 下一阶段顺序

1. 先观察现有 Context 入口是否还有实际延迟；名称查询需要完整消歧，频繁调用优先使用已登记的精确 ID。
2. 索引刷新单独评估增量方案：必须能发现外部新增、编辑、移动与删除，并在异常时回退全量校验。先用隔离 Vault 验证一致性，再比较真实成本。
3. 在证明增量一致性前，保留当前两次完整读取。mtime/size 相同不能证明内容未变；不为省秒数把旧内容伪装成已验证新索引。

本轮没有更改 Vault 内容、写入权限、核验状态或持仓，也没有新增定时器。源码仍由既有稳定入口在下次调用时加载。
