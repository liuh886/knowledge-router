# 功能型 Context：同一套流程，不同用途

Context 不要求一个专用文件夹。它可以指向一篇已有笔记，也可以绑定分散在几个
目录里的材料。以下是使用方式，不是要求用户重排 Vault 的新规范。

| 用途 | 值得长期保留的内容 | 一次更新的例子 |
|---|---|---|
| Research | 假设、实验结果、复现条件、待核实结论 | 今天确认了实验条件，后续安排一次复核 |
| Trip | 已确认安排、变更原因、待确认事项 | 行程时间已确认，但场地仍需跟进 |
| Job | 申请阶段、面试反馈、下一步联络 | 面试完成，等待反馈并记录下次联系时间 |
| 自定义，如设备维护 | 校准、异常、维修、下一次检查 | 记录检测结果，完成原来的检查待办 |

## Agent 应执行的顺序

1. 确认对象：复用已注册的名称、别名和真实材料路径。重名时用 Context id，不能猜。
2. 先读依据：取得相关原文与已明确记录的状态。旧材料里的计划不自动算作当前事实。
3. 预览本次更新：确认事实、记录位置、关联对象及跟进时间；不默认写入专用目录。
4. 在获授权且写入策略允许时提交：一条事件可以追加到原有 Daily，同时关联具体对象。
5. 验证：检查事件回执，再读状态或简报。重试同一事件不能再次写入。

更正状态通过追加一条引用旧事件的新声明完成；完成跟进同样引用前一事件。
逻辑归档只记录 `lifecycle=retired`，不删除笔记。它也不自动取消所有尚未完成的跟进。

## 实现的边界

- 类型名称本身不执行业务流程；目前需要明确的 Context 定义、目标和状态声明。
- 系统不会自动把所有旧日记里的自然语言转换成已确认状态。
- 同一事件不必复制到 Research、Trip 或 Job 页面；它通过外部关联成为该 Context
  可查询的证据。人写的原页面可以保持不动。
- 检查到到期事项不等于已发送通知；有检索入口不等于每个 Agent 的全部生命周期已接通。
- 正式 Vault 仍为只读策略；开发验收中的提交仅在操作系统临时目录中的独立 Vault 执行。

验收代码：`tests/test_context_type_lifecycle.py`。每种用途通过独立 CLI 进程完成
注册、别名规划、预览、追加提交、重试、状态更正、引用简报、到期检查、完成跟进及
逻辑归档，并核对目录不变、原资料不变、日志原字节前缀不变。这验证通用存储和
生命周期能力，不是对自动语义理解、业务建议质量或真实通知投递的验收。

2026-09-09 验收结果：四种类型场景均通过；包含这些场景的全量 Router 回归为
115 项通过（93.43 秒）。真实命令入口的校验值在测试前后保持不变。
